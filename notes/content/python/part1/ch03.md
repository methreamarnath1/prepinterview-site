## 3.1 What is a Variable in Python?

### Definition
> In Python, a variable is a name that refers to (points to) an object stored in memory. The variable itself does not hold the value directly — it holds a reference to the object.

### Easy Meaning
Think of an object as a box sitting somewhere in memory, and a variable as a sticky note with a name on it, pointing at that box. Multiple sticky notes can point at the same box.

### Remember It
**Variable = a name pointing to an object, not a box holding the value itself.**

### Why is it important?
This is different from languages like C, where a variable is literally a memory slot holding a value. In Python, understanding "variables are references" explains almost every confusing behavior around function arguments, copying, and aliasing.

### How it works
1. You write `a = [1, 2, 3]`.
2. Python creates a list object in memory.
3. The name `a` is bound to (points to) that object.
4. If you write `b = a`, no new object is created — `b` simply becomes another name pointing to the *same* object.

### Simple Example
```python
a = [1, 2, 3]
b = a
b.append(4)
print(a)   # [1, 2, 3, 4] -- a "sees" the change because a and b point to the same object
```

### Realistic Example
```python
def add_item(cart):
    cart.append("apple")

my_cart = []
add_item(my_cart)
print(my_cart)   # ['apple'] -- the function modified the same list object the caller has
```
This is exactly how real-world code (like a shopping cart function) relies on shared references to work correctly.

### Common Mistakes
- Believing `b = a` creates a copy of `a`. It doesn't — it creates a second name for the same object.
- Being surprised when a function "accidentally" changes data the caller passed in, because the caller didn't realize it was mutable and shared.

### Interview Question
**Q: How does Python handle variable assignment — does it copy the value?**

### Short Interview Answer
"No, Python doesn't copy the value. A variable is a name bound to an object in memory. When you assign one variable to another, like `b = a`, both names point to the same object — no copy is made. If the object is mutable and you change it through one name, the change is visible through the other name too."

### Detailed Explanation
Every object in Python has an identity, a type, and a value. Assignment just binds a name to an existing object — it does not duplicate data. This is why understanding mutability matters so much: if the object is mutable (like a list), changes made via one reference are visible via all references to that same object. If you want an independent copy, you must explicitly copy it (using `.copy()`, `list()`, or the `copy` module).

### How I Would Answer in an Interview
"In Python, variables don't store values directly — they're more like labels pointing to objects in memory. So when I do `b = a`, I'm not copying the list, I'm just giving the same list a second name. If I mutate it through `b`, I'll see the change through `a` too, since they're literally the same object."

### Follow-up Questions
1. How do you make an actual independent copy? — **`.copy()`, `list(original)`, slicing `[:]`, or `copy.deepcopy()` for nested structures.**
2. What happens if the object is immutable, like an integer? — **You can't mutate it in place at all — any "change" actually creates a brand-new object and rebinds the name.**

### Quick Revision
- Definition: Variable = name pointing to an object, not a value-holding box.
- Interview answer: "Assignment binds a name to an object; it doesn't copy."
- Remember: **Variable = a name pointing to an object, not a box holding the value itself.**

## 3.2 Identity, Type, and Value

### Definition
> Every Python object has three properties: identity (a unique ID that never changes during its life), type (which never changes and determines valid operations), and value (the actual data, which may or may not be changeable).

### Easy Meaning
Every object has a fingerprint (identity), a category (type), and content (value).

### Remember It
**Every object = Identity + Type + Value.**

### Syntax
```python
x = 10
print(id(x))     # identity
print(type(x))    # type
print(x)           # value
```

### Interview Question
**Q: What does `id()` return in Python?**

### Short Interview Answer
"`id()` returns a unique integer that identifies an object during its lifetime. In CPython, this happens to be the object's memory address, though that's an implementation detail, not something the language guarantees."

## 3.3 `is` vs `==`

### Definition
> `==` checks whether two objects have equal *values*. `is` checks whether two names point to the *exact same object* in memory (identity).

### Easy Meaning
`==` asks "do these look the same?" `is` asks "are these literally the same thing?"

### Remember It
**`==` compares value. `is` compares identity.**

### Why does this matter?
Using the wrong one is one of the most common real bugs and interview traps in Python. Using `is` to compare values (like numbers or strings) can work by accident sometimes (due to CPython optimizations) and fail unexpectedly other times.

### Simple Example
```python
a = [1, 2, 3]
b = [1, 2, 3]
print(a == b)   # True  -- same values
print(a is b)   # False -- different objects in memory
```

### Important Differences

| Aspect | `==` | `is` |
|---|---|---|
| Checks | Value equality | Object identity |
| Calls | `__eq__` method | Nothing overridable — raw identity check |
| Typical use | Comparing data | Checking for `None`, singleton checks |

### Common Mistakes
- Using `is` to compare strings or numbers for equality.
- Using `==` when checking for `None` (the convention is `is None`, not `== None`).

### Interview Question
**Q: What is the difference between `is` and `==` in Python?**

### Short Interview Answer
"`==` checks if two objects have the same value, while `is` checks if two variables point to the exact same object in memory. For value comparisons — like checking if two lists have the same contents — we should use `==`. For checking identity, like whether something is `None`, we use `is`."

### Detailed Explanation
`==` calls the object's `__eq__` method, which can be customized to define what "equal" means for a class. `is` cannot be customized — it always checks raw object identity, essentially comparing `id(a) == id(b)`. A common trap is that small integers (-5 to 256) and some strings are cached by CPython, so `is` might accidentally return `True` for equal values — but this is an implementation detail and should never be relied on.

### How I Would Answer in an Interview
"I'd say `==` checks if the values are equal, and `is` checks if it's literally the same object in memory. The classic example is comparing to `None` — we always use `is None` rather than `== None`, because `is` is more explicit and slightly faster there. But for comparing actual data, like two lists, I'd use `==`."

### Common Interview Trap
**Wrong thinking:** "`x is 5` and `x == 5` always behave the same, so it doesn't matter which one I use."
**Correct thinking:** They can behave the same by coincidence for small cached integers, but this isn't guaranteed and shouldn't be relied on — for larger numbers or other objects, `is` can give unexpected `False` results even when values are equal.
**What to say in the interview:** "I always use `==` for value comparisons and reserve `is` specifically for identity checks like `is None`, because relying on CPython's integer caching for `is` comparisons is fragile and not guaranteed by the language."

### Interview Depth Levels
**Basic:** What's the difference between `is` and `==`?
**Intermediate:** Why does `x = 5; y = 5; x is y` return `True`, but the same pattern with larger numbers might return `False`?
**Tricky:** Can two variables holding equal-value, immutable objects always be expected to pass an `is` check? Why or why not?

### Predict the Output
```python
a = "hello"
b = "hello"
print(a is b)

a = "hello world!"
b = "hello world!"
print(a is b)
```
**Answer:** `True`, then likely `False`.
**Explanation:** CPython automatically interns simple identifier-like strings as a memory optimization, but strings with spaces/punctuation are typically not auto-interned. This is a CPython detail, not a guarantee.
**Interview Concept Tested:** Whether the candidate knows not to rely on `is` for string equality.

### Quick Revision
- Definition: `==` = value equality, `is` = identity.
- Interview answer: use `==` for values, `is` only for identity checks (especially `None`).
- Remember: **`==` compares value. `is` compares identity.**

## 3.4 Mutable vs Immutable Objects

### Definition
> A mutable object can be changed after it is created. An immutable object cannot be changed after it is created — any "change" actually creates a brand-new object.

### Easy Meaning
Mutable = you can edit it in place. Immutable = you can't edit it; you have to make a new one if you want something different.

### Remember It
**Mutable = editable. Immutable = fixed forever once created.**

### Important Differences

| Immutable | Mutable |
|---|---|
| `int`, `float`, `bool`, `str`, `tuple`, `frozenset`, `bytes` | `list`, `dict`, `set`, `bytearray`, most custom classes |

### Why is this important?
It affects how functions behave when you pass objects to them, whether an object can be used as a dictionary key, and how much you can trust an object to "stay the same" once created.

### Simple Example
```python
s = "hello"
s[0] = "H"    # TypeError -- strings are immutable

lst = [1, 2, 3]
lst[0] = 99    # Works fine -- lists are mutable
```

### Interview Question
**Q: What is the difference between mutable and immutable objects in Python? Can you give examples?**

### Short Interview Answer
"A mutable object can be changed after creation — like a list, where we can add or remove elements. An immutable object cannot be changed — like a string or a tuple — so any operation that looks like it's modifying it actually creates a new object instead."

### Interview Depth Levels
**Basic:** Give one example each of a mutable and an immutable type.
**Intermediate:** Why are strings immutable in Python? *(Answer: Immutability makes strings hashable — usable as dict keys and set elements — and allows safe sharing/caching of string objects without risk of unexpected changes.)*
**Tricky:** Can an immutable tuple contain a mutable object?
*(Tricky answer: Yes. The tuple itself can't be reassigned or resized, but if it holds a mutable object like a list, that inner list can still be changed. The tuple's immutability only applies to which objects it references, not to whether those objects can change internally.)*

### Predict the Output
```python
t = (1, [2, 3])
t[1].append(4)
print(t)
```
**Answer:** `(1, [2, 3, 4])`
**Explanation:** The tuple's reference to the list never changed — the list object itself was mutated. This doesn't violate tuple immutability.
**Interview Concept Tested:** Whether the candidate understands that immutability applies to the container's references, not necessarily to everything reachable through it.

### Quick Revision
- Definition: Mutable = changeable in place; Immutable = fixed once created.
- Trap: a tuple's own structure is fixed, but it can still hold mutable elements that change.
- Remember: **Mutable = editable. Immutable = fixed forever once created.**

## 3.5 Pass-by-Object-Reference (Function Argument Passing)

### Definition
> Python passes arguments to functions by object reference: the function receives a reference to the same object the caller has. If the object is mutated inside the function, the caller sees the change. If the parameter is reassigned inside the function, that only affects the local name, not the caller's variable.

### Easy Meaning
When you send a variable into a function, you're not sending a copy of the object and you're not directly sending the "real" variable either — you're sending a second sticky note pointing at the same object.

### Remember It
**Mutating inside a function is visible outside. Reassigning inside a function is not.**

### Why is this important?
This is one of the single most common areas of confusion for people coming from other languages, and one of the most frequently tested interview topics.

### Simple Example
```python
def reassign(lst):
    lst = lst + [99]     # creates a NEW object, rebinds the LOCAL name only

def mutate(lst):
    lst.append(99)         # mutates the SAME object

data = [1, 2, 3]
reassign(data)
print(data)   # [1, 2, 3]  -- unaffected

mutate(data)
print(data)   # [1, 2, 3, 99] -- affected
```

### Interview Question
**Q: Does Python pass arguments by value or by reference?**

### Short Interview Answer
"Neither, exactly — Python uses what's called pass-by-object-reference. The function gets a reference to the same object the caller passed in. If the function mutates that object in place, the caller sees the change. But if the function reassigns the parameter to point to a new object, that doesn't affect the caller's variable at all."

### Detailed Explanation
This behavior often confuses people because it doesn't map cleanly onto "pass by value" (as in C, where everything is copied) or "pass by reference" (as in some languages, where the callee can fully replace the caller's variable). In Python, what's passed is a reference to the object — copying the reference, not the object. So mutation is visible to the caller, but rebinding the local parameter name is not, because that only changes what the local name points to, not what the caller's name points to.

### Common Interview Trap
**Wrong thinking:** "Python always passes by reference, so any change inside the function affects the caller."
**Correct thinking:** Only mutation affects the caller. Reassignment inside the function creates a new local binding and does not affect the caller's variable.
**What to say in the interview:** "I'd clarify that it depends on whether the function mutates the object in place or reassigns the parameter — those behave differently, and interviewers often test exactly this distinction."

### Predict the Output
```python
def f(x):
    x += [1]
    return x

lst = [0]
result = f(lst)
print(lst, result)
```
**Answer:** `[0, 1] [0, 1]`
**Explanation:** For a list, `+=` calls `__iadd__`, which mutates the list in place (unlike `x = x + [1]`, which would create a new list and rebind). So both `lst` and `result` point to the same, now-mutated, list.
**Interview Concept Tested:** Whether the candidate knows `+=` behaves differently for mutable vs immutable types.

### Coding Practice
**Beginner:** Write a function that takes a list and appends a value to it, then show the caller's list changed.
**Intermediate:** Write two functions — one that mutates a list parameter, one that reassigns it — and print the caller's variable after calling each, to demonstrate the difference.

### Quick Revision
- Definition: Function args are object references; mutation is visible outside, reassignment is not.
- Interview answer: "Pass-by-object-reference — mutation visible outside, reassignment isn't."
- Remember: **Mutating inside a function is visible outside. Reassigning inside a function is not.**
