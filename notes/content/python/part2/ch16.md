# Chapter 16 — Exceptions In-Depth

## 16.1 The Exception Hierarchy & Basic Handling

### Definition
> An exception is an event that disrupts the normal flow of a program when an error occurs. Python handles exceptions using `try`/`except`/`else`/`finally` blocks. All built-in exceptions inherit from the base class `BaseException`, with most everyday exceptions inheriting from `Exception`.

### Easy Meaning
When something goes wrong while your program runs, Python "raises" an exception — a signal that says "something broke here." You can catch that signal and decide what to do instead of letting the program crash.

### Remember It
**`try` = attempt it. `except` = handle the error. `else` = runs if no error. `finally` = always runs.**

### Simple Example
```python
try:
    result = 10 / 0
except ZeroDivisionError as e:
    print(f"Error: {e}")
else:
    print("No error occurred")
finally:
    print("This always runs")
```

### How it works
1. Python runs the `try` block.
2. If an exception occurs, Python looks for a matching `except` block; if found, it runs that block instead of crashing.
3. If no exception occurred, the `else` block runs (if present).
4. The `finally` block always runs, whether or not an exception occurred — even if the exception wasn't caught.

### Important Differences: `except` vs `finally`

| Aspect | `except` | `finally` |
|---|---|---|
| Runs when | A matching exception occurs | Always, no matter what |
| Purpose | Handle/recover from the error | Cleanup (closing files, releasing resources) |

### Interview Question
**Q: What's the difference between `else` and `finally` in a `try` block?**

### Short Interview Answer
"`else` runs only if the `try` block completed without raising an exception. `finally` runs no matter what happens — whether there was an exception, whether it was caught, or even if there was a `return` statement inside the `try` block. `finally` is typically used for cleanup work, like closing a file or releasing a resource."

### Common Interview Trap
**Wrong thinking:** "If I `return` inside `try`, the `finally` block gets skipped."
**Correct thinking:** `finally` runs even if `try` (or `except`) contains a `return` statement — Python runs the `finally` block before actually returning.
**What to say in the interview:** "I'd point out that `finally` always executes, even around a `return` — that's exactly why it's the reliable place to put cleanup code."

## 16.2 Custom Exceptions

### Definition
> A custom exception is a user-defined class that inherits from `Exception` (or a more specific built-in exception), used to represent application-specific error conditions with meaningful names.

### Simple Example
```python
class InsufficientFundsError(Exception):
    pass

def withdraw(balance, amount):
    if amount > balance:
        raise InsufficientFundsError("Not enough balance!")
    return balance - amount

try:
    withdraw(100, 150)
except InsufficientFundsError as e:
    print(e)
```

### Interview Question
**Q: Why would you create a custom exception instead of using a built-in one?**

### Short Interview Answer
"Custom exceptions make errors more meaningful and specific to your application's domain — for example, `InsufficientFundsError` is much clearer than a generic `ValueError`. They also let calling code catch specific application errors separately from unrelated built-in errors, which makes error handling more precise."

## 16.3 Exception Chaining (`raise ... from ...`)

### Definition
> Exception chaining lets you raise a new exception while preserving the original exception that caused it, using `raise NewException(...) from original_exception`.

### Simple Example
```python
try:
    1 / 0
except ZeroDivisionError as e:
    raise ValueError("Invalid calculation") from e
```

### Interview Question
**Q: What does `raise ... from ...` do?**

### Short Interview Answer
"It lets you raise a new exception while keeping a reference to the original exception that triggered it, so the traceback shows both — the root cause and the new, higher-level error. This is really useful for debugging, since you don't lose the original error's context when you wrap it in a more descriptive exception."

### Coding Practice
**Beginner:** Write a function that catches a `ValueError` when converting user input to an integer, printing a friendly message instead of crashing.
**Intermediate:** Create a custom exception hierarchy for a simple banking app (`BankError` as a base, with `InsufficientFundsError` and `InvalidAccountError` as subclasses).

- Definition: `try`/`except`/`else`/`finally` handle errors gracefully.
- Trap: `finally` always runs, even around `return`.
- Custom exceptions = meaningful, domain-specific errors.
- Remember: **`try` = attempt it. `except` = handle. `else` = if no error. `finally` = always.**
