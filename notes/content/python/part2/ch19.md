# Chapter 19 — OOP Mechanics: Methods, MRO, Properties, Magic Methods, Dataclasses

## 19.1 Instance Methods vs Class Methods vs Static Methods

### Definition
> An instance method operates on a specific object and automatically receives `self`. A class method operates on the class itself and receives `cls` instead, marked with `@classmethod`. A static method doesn't automatically receive either `self` or `cls` — it's just a regular function logically grouped inside the class, marked with `@staticmethod`.

### Easy Meaning
Instance method = "needs a specific object to work on." Class method = "works with the class itself, not one specific object." Static method = "doesn't need the object OR the class — just lives inside the class for organization."

### Remember It
**Instance method → `self`. Class method → `cls`. Static method → neither.**

### Simple Example
```python
class Pizza:
    total_pizzas = 0

    def __init__(self, size):
        self.size = size
        Pizza.total_pizzas += 1

    def describe(self):                     # instance method
        return f"A {self.size} pizza"

    @classmethod
    def from_total_count(cls):                 # class method
        return f"{cls.total_pizzas} pizzas made so far"

    @staticmethod
    def is_valid_size(size):                       # static method
        return size in ("small", "medium", "large")

p = Pizza("medium")
print(p.describe())                    # instance method needs an object
print(Pizza.from_total_count())          # class method works via the class
print(Pizza.is_valid_size("large"))        # static method: no self/cls needed
```

### Important Differences

| Aspect | Instance Method | Class Method | Static Method |
|---|---|---|---|
| First param | `self` | `cls` | none required |
| Access instance data | Yes | No | No |
| Access class data | Yes | Yes | No |
| Decorator | none | `@classmethod` | `@staticmethod` |
| Typical use | Normal object behavior | Alternative constructors, class-wide operations | Utility/helper logic related to the class |

### Interview Question
**Q: What's the difference between `@staticmethod` and `@classmethod`?**

### Short Interview Answer
"A `classmethod` receives the class itself as its first argument, conventionally called `cls`, so it can access or modify class-level data, and it's often used for alternative constructors. A `staticmethod` doesn't automatically receive the instance or the class at all — it behaves like a plain function that's just grouped inside the class for organizational purposes, because it's logically related but doesn't need access to instance or class state."

### Common Interview Trap
**Wrong thinking:** "`@staticmethod` and `@classmethod` are basically the same thing, just different names."
**Correct thinking:** `classmethod` explicitly receives the class (`cls`) and can interact with class-level state or create alternate constructors; `staticmethod` receives neither and cannot access class or instance state directly through an automatic parameter.
**What to say in the interview:** "I'd use `classmethod` when I need access to the class itself, like for an alternative constructor, and `staticmethod` when the method is just logically related to the class but doesn't need any class or instance data at all."

## 19.2 Multiple Inheritance, MRO, and `super()`

### Definition
> Multiple inheritance means a class can inherit from more than one parent class. The MRO (Method Resolution Order) is the specific order Python searches through parent classes to find a method or attribute. `super()` gives access to methods from the next class in that MRO, not necessarily the immediate parent.

### Easy Meaning
When a class has multiple parents, Python needs a clear rule for "which parent's version of a method wins if there's a conflict?" That rule is the MRO. `super()` is how you call "the next one in line," following that same rule.

### Remember It
**MRO = the order Python checks classes when looking something up. `super()` follows the MRO, not just "the direct parent."**

### Simple Example
```python
class A:
    def greet(self):
        return "A"

class B(A):
    def greet(self):
        return "B -> " + super().greet()

class C(A):
    def greet(self):
        return "C -> " + super().greet()

class D(B, C):
    def greet(self):
        return "D -> " + super().greet()

print(D().greet())
print(D.__mro__)
```
**Output:** `D -> B -> C -> A` and the MRO shows `D, B, C, A, object` — this follows the **C3 linearization algorithm**, which Python uses to compute a consistent order even in multiple inheritance ("diamond problem") scenarios.

### Interview Question
**Q: What is MRO, and why does it matter?**

### Short Interview Answer
"MRO stands for Method Resolution Order — it's the order Python follows when looking for a method or attribute across a class's inheritance chain, especially important with multiple inheritance. Python uses an algorithm called C3 linearization to compute a consistent, predictable order, so that even in complex inheritance structures — like the diamond problem, where two parent classes share a common ancestor — there's no ambiguity about which method actually gets called. You can check it directly using `ClassName.__mro__` or `ClassName.mro()`."

### Detailed Explanation
`super()` doesn't simply mean "call my direct parent's method" — that's a common misconception. It actually means "call the next class in the MRO, relative to the current class." In single inheritance this looks the same as calling the direct parent, but in multiple inheritance, it can point to a sibling class instead, which is exactly what allows cooperative multiple inheritance to work correctly, as seen in the example above where `D`'s `super()` calls `B`, whose `super()` calls `C` (not `A` directly), following the computed MRO.

### Common Interview Trap
**Wrong thinking:** "`super()` always calls the immediate parent class's method."
**Correct thinking:** `super()` calls the next class in the MRO — which, in multiple inheritance, might be a sibling class rather than the direct parent.
**What to say in the interview:** "I'd clarify that `super()` follows the MRO, not just the direct parent — that distinction becomes really important in multiple inheritance scenarios like the diamond problem."

### Predict the Output
```python
class A:
    def greet(self):
        print("A")

class B(A):
    def greet(self):
        print("B")
        super().greet()

class C(A):
    def greet(self):
        print("C")
        super().greet()

class D(B, C):
    def greet(self):
        print("D")
        super().greet()

D().greet()
```
**Answer:**
```
D
B
C
A
```
**Explanation:** The MRO for `D` is `D → B → C → A → object`. Each `super().greet()` call moves to the next class in this order, not directly to each class's own "parent" in the traditional sense.
**Interview Concept Tested:** True understanding of MRO vs the common misconception of "super = direct parent."

## 19.3 Properties

### Definition
> A property lets you define a method that behaves like a regular attribute when accessed, allowing you to add logic (like validation) to attribute access without changing how it's used from outside the class.

### Simple Example
```python
class Circle:
    def __init__(self, radius):
        self._radius = radius

    @property
    def radius(self):
        return self._radius

    @radius.setter
    def radius(self, value):
        if value < 0:
            raise ValueError("Radius can't be negative")
        self._radius = value

c = Circle(5)
print(c.radius)     # looks like attribute access, but calls the getter method
c.radius = 10          # calls the setter method, with validation
```

### Interview Question
**Q: What is a property in Python, and why would you use one?**

### Short Interview Answer
"A property lets a method be accessed like a regular attribute, using `@property` for the getter and `@x.setter` for the setter. It's useful when you want to add validation or computed logic to an attribute, without breaking the simple `object.attribute` syntax that users of the class expect."

## 19.4 Operator Overloading & Magic Methods (Introduction)

### Definition
> Operator overloading means defining how built-in operators (like `+`, `==`, `<`) behave for your own custom classes, by implementing special "magic" (dunder) methods like `__add__`, `__eq__`, `__lt__`.

### Simple Example
```python
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

    def __add__(self, other):
        return Point(self.x + other.x, self.y + other.y)

    def __repr__(self):
        return f"Point({self.x}, {self.y})"

p1 = Point(1, 2)
p2 = Point(3, 4)
print(p1 + p2)   # Point(4, 6) -- calls __add__ automatically
```

### Interview Question
**Q: What is operator overloading in Python?**

### Short Interview Answer
"Operator overloading means defining how a built-in operator behaves for a custom class, by implementing special methods like `__add__` for `+` or `__eq__` for `==`. It lets our own objects support natural, intuitive syntax, like adding two `Point` objects together with `+`, instead of needing a separately named method."

## 19.5 Dataclasses

### Definition
> `@dataclass` is a decorator from the `dataclasses` module that automatically generates common boilerplate methods — like `__init__`, `__repr__`, and `__eq__` — for classes that are mainly used to store data.

### Easy Meaning
Instead of writing `__init__`, `__repr__`, and `__eq__` by hand for a simple data-holding class, `@dataclass` writes them for you automatically.

### Remember It
**`@dataclass` = auto-generates `__init__`, `__repr__`, `__eq__` for simple data-holding classes.**

### Simple Example
```python
from dataclasses import dataclass

@dataclass
class Point:
    x: int
    y: int

p1 = Point(1, 2)
p2 = Point(1, 2)
print(p1)          # Point(x=1, y=2) -- auto-generated __repr__
print(p1 == p2)      # True -- auto-generated __eq__ (compares field values)
```

### Interview Question
**Q: What is a dataclass, and what does it save you from writing?**

### Short Interview Answer
"A dataclass is a decorator that automatically generates common methods like `__init__`, `__repr__`, and `__eq__` for classes that are mostly meant to hold data. Instead of writing that boilerplate by hand, you just declare the fields with type hints, and the dataclass decorator fills in the rest — it makes simple data-holding classes much shorter and less error-prone."

### Coding Practice
**Beginner:** Convert a manually written `Person` class (with `__init__`, `__repr__`, `__eq__`) into a `@dataclass`.
**Intermediate:** Write a class hierarchy using multiple inheritance, then print its `__mro__` and explain the order.

### Quick Revision
- Instance method → `self`; class method → `cls`; static method → neither.
- MRO = C3-linearized lookup order; `super()` follows MRO, not just direct parent.
- Properties = attribute-like access with logic behind it.
- Dataclasses auto-generate `__init__`/`__repr__`/`__eq__` for simple data classes.
- Remember: **Instance method → `self`. Class method → `cls`. Static method → neither. `super()` follows the MRO.**
