### 1.1 What Is the Python Data Model?

#### Definition
> The Python Data Model is the formal set of rules that defines how every object in Python behaves — how it is created, how it is compared, how it is printed, how it responds to operators, and how attributes on it are looked up. It works through special methods, called "dunder methods" (double-underscore methods), such as `__init__`, `__str__`, and `__eq__`.

#### Easy Meaning
Every object in Python secretly implements a set of "hooks." When you write `len(x)`, Python doesn't have special-case code for every type — it just calls `x.__len__()`. The data model is the full list of these hooks.

#### Remember It
**Data Model = the dunder-method contract every Python object follows.**

#### Why Is It Used?
Python is designed so that built-in syntax (`+`, `len()`, `for`, `print()`, `x[0]`) works the same way on both built-in types and your own classes. Instead of hardcoding special cases, Python calls a dunder method behind the scenes. This is why you can make your own class support `+`, iteration, indexing, or comparison — you just implement the right dunder method.

#### How It Works
1. You write ordinary-looking code: `a + b`, `print(obj)`, `obj[3]`.
2. Python translates this into a dunder-method call: `a.__add__(b)`, `print()` calls `str(obj)` which calls `obj.__str__()`, `obj[3]` calls `obj.__getitem__(3)`.
3. Python looks up the dunder method **on the type**, not the instance (important internal detail — see §1.6).
4. The method executes and returns a value, which becomes the result of the original expression.

#### CPYTHON IMPLEMENTATION DETAIL vs PYTHON LANGUAGE GUARANTEE
- **Language guarantee:** operators and built-ins dispatch to dunder methods.
- **CPython detail:** dunder-method lookup for implicit invocations (like `a + b`) bypasses instance `__dict__` and goes straight to the type's slot — this is a CPython optimization detail, but it's specified behavior in the data model, not an accident.

### 1.2 `__new__` vs `__init__`

#### Definition
> `__new__` is the method that **creates** a new, empty instance of a class and returns it. `__init__` is the method that **initializes** the attributes of an already-created instance. `__new__` runs first; `__init__` runs second, on the object `__new__` returned.

#### Easy Meaning
`__new__` builds the empty house. `__init__` moves furniture into it.

#### Remember It
**`__new__` creates the object. `__init__` sets it up.**

#### Why Is It Used?
Most of the time you never touch `__new__` — `__init__` is enough. But `__new__` matters when:
- You subclass an immutable type (`int`, `str`, `tuple`) and need to control creation, since immutable objects can't be modified in `__init__`.
- You're implementing a singleton or a caching pattern (return an existing instance instead of a new one).
- You're writing a metaclass.

#### Syntax
```python
class Point:
    def __new__(cls, *args, **kwargs):
        print("Creating instance")
        instance = super().__new__(cls)
        return instance

    def __init__(self, x, y):
        print("Initializing instance")
        self.x = x
        self.y = y
```

#### Simple Example
```python
class Demo:
    def __new__(cls):
        print("new called")
        return super().__new__(cls)

    def __init__(self):
        print("init called")

d = Demo()
```
**Output:**
```
new called
init called
```

#### Realistic Example — Singleton Pattern
```python
class Logger:
    _instance = None

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance

log1 = Logger()
log2 = Logger()
print(log1 is log2)   # True
```
This is a common interview task: "implement a singleton in Python."

#### Common Mistakes
- Forgetting that `__new__` is a **static method** implicitly (it takes `cls`, not `self`), even though you don't write `@staticmethod`.
- Calling `cls()` inside `__new__` instead of `super().__new__(cls)` — causes infinite recursion.
- Assuming `__init__` always runs — if `__new__` returns an instance of a **different class**, `__init__` is skipped.

#### Important Difference Table

| Aspect | `__new__` | `__init__` |
|---|---|---|
| Purpose | Creates the object | Initializes the object |
| Return value | Must return an object (usually the instance) | Must return `None` |
| Runs on | The class (`cls`) | The instance (`self`) |
| Called for immutables | Yes — needed for `int`/`str` subclasses | Runs after, often too late for immutables |
| Implicit type | Static method | Instance method |

#### Interview Question
**Q: What is the difference between `__new__` and `__init__`?**

**Short Interview Answer:**
"`__new__` is responsible for creating a new instance of a class and returning it, while `__init__` initializes that instance by setting its attributes. `__new__` runs first and receives the class as its first argument, and `__init__` runs afterward on the object that `__new__` returned. Most of the time we only override `__init__`, but `__new__` is important when subclassing immutable types or implementing patterns like singletons."

**Detailed Explanation:**
When you call `Point(1, 2)`, Python actually calls `Point.__new__(Point, 1, 2)` first to get an object, then calls `obj.__init__(1, 2)` on that object. If `__new__` returns an instance that isn't of the class being constructed (or a subclass), `__init__` is never called on it at all — this is a common source of confusion.

#### Follow-up Questions
1. Why would you override `__new__` instead of `__init__`?
   *Because immutable objects can't be modified after creation, so any setup must happen during creation, in `__new__`.*
2. What happens if `__new__` returns an object of an unrelated class?
   *`__init__` is not called on it.*
3. Is `__new__` a static method or instance method?
   *Implicitly static — it takes `cls`, not `self`, even without the decorator.*

#### Predict the Output
```python
class A:
    def __new__(cls):
        print("A.__new__")
        return object.__new__(cls)
    def __init__(self):
        print("A.__init__")

class B(A):
    def __new__(cls):
        print("B.__new__")
        return "not an instance"

b = B()
print(type(b))
```
**Answer:**
```
B.__new__
<class 'str'>
```
**Explanation:** `B.__new__` returns a plain string, not a `B` instance. Since the returned object is not an instance of `B`, `__init__` is **never called**, and `A.__new__` never runs since `B.__new__` didn't call `super().__new__`.

**Interview Concept Tested:** Whether the candidate understands that `__init__` is conditional on `__new__`'s return type — a very common trap.

#### Common Interview Trap
**Wrong thinking:** "`__init__` always runs after an object is constructed."
**Correct thinking:** `__init__` only runs if `__new__` returns an instance of the class (or subclass) being constructed.
**What to say in the interview:** "Init is called by `type.__call__` only when `isinstance(new_instance, cls)` is true — so it's conditional."

#### Quick Revision
- Definition: `__new__` creates, `__init__` initializes.
- Key point: `__new__` is implicitly static, takes `cls`.
- Common mistake: infinite recursion by calling `cls()` inside `__new__`.
- Trap: `__init__` skipped if `__new__` returns wrong type.
- Remember: **New builds it, Init fills it.**

### 1.3 Attribute Lookup: `__getattr__` vs `__getattribute__` vs `__setattr__` vs `__delattr__`

#### Definition
> `__getattribute__` is called for **every** attribute access on an object, without exception. `__getattr__` is called **only when normal lookup fails** (attribute not found through the usual mechanisms). `__setattr__` intercepts attribute assignment, and `__delattr__` intercepts attribute deletion.

#### Easy Meaning
- `__getattribute__` = "Every single time someone asks for an attribute, I get first say."
- `__getattr__` = "Only called in as a fallback, when nothing else found it."

#### Remember It
**`__getattribute__` = always. `__getattr__` = only on failure.**

#### Why Is It Used?
These hooks let you build things like:
- Lazy attributes (compute a value only when first accessed).
- Proxy/wrapper objects.
- Dynamic APIs (e.g., ORMs that let you write `user.name` even though `name` isn't a real attribute).
- Logging/debugging every attribute access.

#### How It Works — Attribute Lookup Order (very important internal detail)
When you write `obj.x`, CPython does roughly this:
1. Calls `type(obj).__getattribute__(obj, "x")`.
2. Default `__getattribute__` looks in:
   a. `type(obj).__dict__` and its MRO, specifically checking for **data descriptors** first.
   b. `obj.__dict__` (instance dictionary).
   c. `type(obj).__dict__` again for non-data descriptors / class attributes.
3. If all of that fails, Python calls `__getattr__(obj, "x")` **if it's defined** — this is the fallback.
4. If `__getattr__` isn't defined or also fails, `AttributeError` is raised.

#### Syntax
```python
class Lazy:
    def __getattr__(self, name):
        print(f"{name} not found normally, computing it")
        value = name.upper()
        setattr(self, name, value)   # cache it
        return value
```

#### Simple Example
```python
class Demo:
    def __getattr__(self, name):
        return f"No attribute called '{name}'"

d = Demo()
print(d.anything)
```
**Output:** `No attribute called 'anything'`

#### Realistic Example — Attribute Logger
```python
class Traced:
    def __init__(self):
        self.x = 10

    def __getattribute__(self, name):
        print(f"Accessing: {name}")
        return super().__getattribute__(name)

t = Traced()
print(t.x)
```
**Output:**
```
Accessing: x
10
```
Note: even `self.x = 10` in `__init__` triggers `__setattr__`, but reading `t.x` triggers `__getattribute__` — every time, for every attribute, including `__init__` itself and dunder lookups internally (careful: this can cause infinite recursion if not handled with `super()`).

#### Common Mistakes
- Overriding `__getattribute__` and forgetting to call `super().__getattribute__()` — causes infinite recursion, since every internal attribute access (even `self.__dict__`) goes through it.
- Confusing `__getattr__` with `__getattribute__` — thinking `__getattr__` runs for every access (it doesn't; only on failure).
- Implementing `__getattr__` in a way that raises something other than `AttributeError` — this breaks `hasattr()`, since `hasattr()` relies on catching `AttributeError`.

#### Important Difference Table

| Method | Called when | Common use |
|---|---|---|
| `__getattribute__` | Every attribute access | Logging, proxies, full control |
| `__getattr__` | Only if normal lookup fails | Lazy attributes, dynamic APIs |
| `__setattr__` | Every attribute assignment | Validation, read-only objects |
| `__delattr__` | Every attribute deletion | Prevent deletion, cleanup |

#### Interview Question
**Q: What's the difference between `__getattr__` and `__getattribute__`?**

**Short Interview Answer:**
"`__getattribute__` is called for every attribute access on an object, so if you override it, you're intercepting everything. `__getattr__` is only called when the normal attribute lookup fails — it's a fallback mechanism. Most custom classes use `__getattr__` because it's safer and less likely to cause infinite recursion. `__getattribute__` is used when you need to intercept absolutely every access, like in proxy objects."

#### Follow-up Questions
1. Why is overriding `__getattribute__` risky?
   *Because it's called for every attribute access, including internal ones — if you're not careful, you cause infinite recursion by accessing `self.x` inside `__getattribute__` itself.*
2. Does `__getattr__` get called for attributes that exist normally?
   *No — only when lookup fails.*
3. What exception must `__getattr__` raise for `hasattr()` to work correctly?
   *`AttributeError`.*

#### Predict the Output
```python
class Config:
    def __getattr__(self, name):
        return "default"

c = Config()
c.timeout = 30
print(c.timeout)
print(c.missing_key)
```
**Answer:**
```
30
default
```
**Explanation:** `c.timeout` was explicitly set, so normal lookup succeeds and `__getattr__` is never called. `c.missing_key` was never set, so lookup fails and `__getattr__` provides the fallback.

**Interview Concept Tested:** Understanding that `__getattr__` is a fallback, not an interceptor.

#### Common Interview Trap
**Wrong thinking:** "If I define `__getattr__`, it runs before every attribute lookup."
**Correct thinking:** `__getattr__` only fires *after* the normal mechanism (instance `__dict__`, class `__dict__`, descriptors) has already failed.
**What to say in the interview:** "`__getattr__` is the fallback of last resort, not an interceptor — that's `__getattribute__`'s job."

#### Quick Revision
- `__getattribute__`: always called.
- `__getattr__`: called only on failure.
- `__setattr__` / `__delattr__`: intercept assignment/deletion.
- Trap: overriding `__getattribute__` without `super()` → infinite recursion.
- Remember: **Attribute = always. Attr = fallback.**

### 1.4 `__dict__` and `__class__`

#### Definition
> `__dict__` is a dictionary that stores an object's writable attributes (unless the class uses `__slots__`). `__class__` is a reference from an instance back to the class that created it.

#### Easy Meaning
`__dict__` is where your object's data actually lives. `__class__` tells you "who made me."

#### Simple Example
```python
class Person:
    def __init__(self, name):
        self.name = name

p = Person("Amar")
print(p.__dict__)   # {'name': 'Amar'}
print(p.__class__)  # <class '__main__.Person'>
print(type(p) is p.__class__)  # True
```

#### Common Mistakes
- Assuming every object has `__dict__` — objects of classes using `__slots__` do not (covered in the Memory Management chapter).
- Confusing `p.__class__` with `Person` itself — `p.__class__` is a reference *to* `Person`, evaluated dynamically (which matters for proxy/metaclass tricks where it can be overridden).

#### Interview Question
**Q: Where does an object store its instance attributes?**

**Short Interview Answer:**
"By default, in a dictionary accessible through `__dict__`. When you write `self.name = name`, Python is really doing `self.__dict__['name'] = name` behind the scenes. Classes that use `__slots__` don't get a `__dict__`, which saves memory but restricts you to a fixed set of attributes."

#### Quick Revision
- `__dict__`: instance's attribute storage.
- `__class__`: pointer to the object's class.
- Trap: `__slots__` classes have no `__dict__`.

### 1.5 Method Binding, Bound Methods, and Callable Objects

#### Definition
> When you access a method through an instance (`obj.method`), Python creates a **bound method** — a callable that already has `self` filled in. When you access it through the class (`Class.method`), you get the plain function, unbound. Any object can become callable by defining `__call__`.

#### Easy Meaning
`obj.method` isn't just a function — it's a little package containing the function *and* the object it belongs to, so you don't have to pass `self` yourself.

#### How It Works
1. Functions are **non-data descriptors** (see Descriptors chapter) — this is *why* method binding works at all.
2. `obj.method` triggers `function.__get__(obj, type(obj))`, which returns a `bound method` object.
3. Calling the bound method automatically supplies `obj` as the first argument (`self`).

#### Simple Example
```python
class Greeter:
    def hello(self):
        return "hi"

g = Greeter()
bound = g.hello
print(bound)          # <bound method Greeter.hello of <...>>
print(bound())        # "hi" — self was auto-filled
print(Greeter.hello)  # <function Greeter.hello at ...> (unbound function)
print(Greeter.hello(g))  # "hi" — self passed manually
```

#### Callable Objects — `__call__`
```python
class Multiplier:
    def __init__(self, factor):
        self.factor = factor
    def __call__(self, x):
        return x * self.factor

double = Multiplier(2)
print(double(5))   # 10 — the instance itself is called like a function
print(callable(double))  # True
```

#### Why Is It Used?
`__call__` lets you build objects that behave like functions but carry state — useful for decorators-as-classes, configurable strategies, and memoization caches.

#### Interview Question
**Q: What does it mean for a method to be "bound"?**

**Short Interview Answer:**
"A bound method is a method that's already associated with a specific instance, so calling it doesn't require passing `self` manually. When you access `obj.method`, Python's descriptor protocol automatically binds `obj` as the first argument. If you access the same method through the class instead, like `Class.method`, you get the plain unbound function and have to pass the instance yourself."

#### Predict the Output
```python
class A:
    def show(self):
        return id(self)

a = A()
m1 = a.show
m2 = a.show
print(m1 == m2)
print(m1 is m2)
```
**Answer:**
```
True
False
```
**Explanation:** Bound methods compare equal if they wrap the same function and same instance, but each access to `a.show` creates a **new bound-method object**, so `is` returns `False`.

**Interview Concept Tested:** Understanding that bound methods are created fresh on each access — a subtle but real trap.

#### Common Interview Trap
**Wrong thinking:** "`a.show is a.show` should be `True` since it's the same method."
**Correct thinking:** Each attribute access creates a new bound-method wrapper object; equality is defined, but identity isn't guaranteed.

#### Quick Revision
- Bound method = function + instance, auto-fills `self`.
- `Class.method` = unbound plain function.
- `__call__` makes any object callable.
- Trap: `a.method is a.method` → `False`.

### 1.6 `__str__` vs `__repr__`

#### Definition
> `__repr__` returns an unambiguous, developer-facing string representation of an object — ideally one that could recreate the object. `__str__` returns a readable, user-facing string. If `__str__` is not defined, Python falls back to `__repr__`.

#### Easy Meaning
`__repr__` is for programmers debugging. `__str__` is for end users reading output.

#### Remember It
**`repr` = for the developer. `str` = for the user.**

#### Syntax & Example
```python
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __repr__(self):
        return f"Point(x={self.x}, y={self.y})"
    def __str__(self):
        return f"({self.x}, {self.y})"

p = Point(1, 2)
print(p)          # calls __str__  -> (1, 2)
print(repr(p))    # calls __repr__ -> Point(x=1, y=2)
print([p])        # list printing uses __repr__ -> [Point(x=1, y=2)]
```

#### Important Difference Table

| Aspect | `__repr__` | `__str__` |
|---|---|---|
| Audience | Developers | End users |
| Goal | Unambiguous, ideally `eval()`-able | Readable |
| Called by | `repr()`, interactive shell, containers | `str()`, `print()` |
| Fallback | None (always define this one) | Falls back to `__repr__` if missing |

#### Common Mistakes
- Defining only `__str__` and expecting it to be used inside a list or debugger — containers always use `__repr__` for their elements.
- Making `__repr__` vague like `"<Point object>"` — it should ideally show enough to recreate or identify the object.

#### Interview Question
**Q: What's the difference between `__str__` and `__repr__`, and which should you always implement?**

**Short Interview Answer:**
"`__repr__` gives an unambiguous representation meant for developers and debugging, ideally something you could copy-paste to recreate the object. `__str__` gives a nicer, human-readable representation for end users. If a class doesn't define `__str__`, Python falls back to `__repr__`, so as a best practice you should always define `__repr__`, and add `__str__` only if you need a different, friendlier version for users."

#### Quick Revision
- `__repr__`: unambiguous, for developers, always implement.
- `__str__`: readable, for users, falls back to `__repr__`.
- Containers (list, dict) always use `__repr__` for elements.

### 1.7 `__eq__` and `__hash__` — The Equality/Hashing Contract

#### Definition
> `__eq__` defines what it means for two objects to be equal (`==`). `__hash__` returns an integer used to place an object into hash-based collections like `dict` and `set`. Python enforces a contract: **if two objects are equal, they must have the same hash.**

#### Easy Meaning
If you say "these two things are equal," Python expects them to land in the same "bucket" in a dictionary or set. Breaking that rule breaks dictionaries and sets silently.

#### Why Is It Used?
Dictionaries and sets use the hash value to find the right bucket quickly (average O(1) lookup), then use `__eq__` to confirm an exact match within that bucket. If hash and equality disagree, lookups fail unpredictably.

#### How It Works — The Default Behavior
1. By default, every object inherits `__eq__` from `object`, which compares by **identity** (`is`).
2. By default, every object inherits `__hash__` from `object`, based on `id()`.
3. **The moment you define `__eq__` yourself, Python automatically sets `__hash__` to `None`**, making your object unhashable — unless you also explicitly define `__hash__`.

#### Simple Example
```python
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __eq__(self, other):
        return isinstance(other, Point) and (self.x, self.y) == (other.x, other.y)

p1 = Point(1, 2)
p2 = Point(1, 2)
print(p1 == p2)     # True — because __eq__ compares values
print({p1, p2})     # TypeError: unhashable type: 'Point'
```
**Why the error?** Defining `__eq__` set `__hash__` to `None` automatically.

#### Fixing It
```python
class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y
    def __eq__(self, other):
        return isinstance(other, Point) and (self.x, self.y) == (other.x, other.y)
    def __hash__(self):
        return hash((self.x, self.y))

s = {Point(1, 2), Point(1, 2)}
print(len(s))   # 1 — treated as duplicates
```

#### Common Mistakes
- Defining `__eq__` without `__hash__` and being confused why the object can no longer go in a `set` or be a dict key.
- Making `__hash__` inconsistent with `__eq__` (e.g., hashing on a mutable field that changes) — this silently breaks dictionary lookups: the object "disappears" from the set once its hash changes.
- Using mutable objects as dict keys / set members at all — generally discouraged, since mutating them after insertion corrupts the hash table.

#### Important Difference Table

| Rule | Explanation |
|---|---|
| `a == b` ⟹ `hash(a) == hash(b)` | Required contract |
| `hash(a) == hash(b)` ⟹ `a == b` | **NOT** required (hash collisions are allowed) |
| Defining `__eq__` | Auto-sets `__hash__ = None` unless you define it |
| Immutable + hashable objects | Safe as dict keys / set members |
| Mutable + hashable objects | Dangerous — hash can change after insertion |

#### Interview Question
**Q: Why does defining `__eq__` make an object unhashable by default?**

**Short Interview Answer:**
"Python enforces a rule that equal objects must produce equal hashes, since dictionaries and sets rely on the hash to locate an object's bucket. If I customize `__eq__` without also customizing `__hash__`, Python can't guarantee that contract anymore — the default identity-based hash would violate it. So Python plays it safe and sets `__hash__` to `None`, making the object unhashable, until I explicitly provide a compatible `__hash__` myself."

#### Predict the Output
```python
class Item:
    def __init__(self, key):
        self.key = key
    def __eq__(self, other):
        return self.key == other.key
    def __hash__(self):
        return hash(self.key)

a = Item(1)
b = Item(1)
d = {a: "first"}
d[b] = "second"
print(len(d))
print(d[a])
```
**Answer:**
```
1
second
```
**Explanation:** `a` and `b` are equal and have the same hash, so `d[b] = "second"` overwrites the same slot as `a` rather than adding a new one.

**Interview Concept Tested:** Whether the candidate understands hash+equality determine dictionary key identity, not object identity.

#### Common Interview Trap
**Wrong thinking:** "Two different objects can never be the same dictionary key."
**Correct thinking:** Any two objects that are `__eq__`-equal and hash-equal are treated as the *same key*, regardless of `is` identity.
**What to say in the interview:** "Dictionary key equality is based on `__eq__` and `__hash__`, not object identity — that's exactly the contract Python enforces."

#### Quick Revision
- `__eq__` defines equality; `__hash__` defines bucket placement.
- Contract: equal objects must hash equal (not the reverse).
- Defining `__eq__` disables default `__hash__` unless redefined.
- Never use mutable fields for hashing if the object goes into a set/dict.
