# Chapter 11: Concurrency I — Threading

### 11.1 What Is a Thread?

**Definition:** A thread is an independent sequence of execution within a process, sharing the same memory space as other threads in that process.

**Why It's Used:** Threads are useful for **I/O-bound** work — tasks that spend most of their time waiting (network calls, file I/O, database queries) — because while one thread waits, another can run.

### 11.2 The GIL (Global Interpreter Lock)

**Definition:** The GIL is a mutex in CPython that allows only **one thread to execute Python bytecode at a time**, even on multi-core machines.

**Why It Exists:** It simplifies CPython's memory management (reference counting isn't thread-safe without it) at the cost of true CPU-bound parallelism within a single process.

**CRITICAL DISTINCTION:**

| Workload Type | Threading helps? | Why |
|---|---|---|
| I/O-bound (network, disk, DB) | **Yes** | GIL is released during I/O waits |
| CPU-bound (heavy computation) | **No** | GIL prevents true parallel execution of Python bytecode |

**PYTHON LANGUAGE GUARANTEE vs CPYTHON DETAIL:** The GIL is a **CPython implementation detail** (not shared by Jython, IronPython, and being experimentally removed in newer CPython "free-threaded" builds) — it is not part of the Python language specification itself.

### 11.3 Basic Threading Syntax
```python
import threading
import time

def worker(name):
    print(f"{name} starting")
    time.sleep(1)
    print(f"{name} done")

t1 = threading.Thread(target=worker, args=("Thread-A",))
t2 = threading.Thread(target=worker, args=("Thread-B",))
t1.start()
t2.start()
t1.join()
t2.join()
print("All threads finished")
```
**Why `join()` matters:** Without it, the main program could finish (and exit) before the threads complete.

### 11.4 Race Conditions

**Definition:** A race condition occurs when the outcome of a program depends on the unpredictable timing/interleaving of multiple threads accessing shared data.

```python
import threading

counter = 0
def increment():
    global counter
    for _ in range(100000):
        counter += 1   # NOT atomic! Read-modify-write across 3 bytecode steps

threads = [threading.Thread(target=increment) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)   # Often NOT 200000 — race condition!
```
**Why:** `counter += 1` is not a single atomic operation — it's read, add, write. The GIL can switch threads between these steps, causing lost updates.

### 11.5 Locks — `threading.Lock`

```python
import threading

counter = 0
lock = threading.Lock()

def safe_increment():
    global counter
    for _ in range(100000):
        with lock:
            counter += 1

threads = [threading.Thread(target=safe_increment) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)   # Always 200000 — protected by lock
```

### 11.6 Other Synchronization Primitives

| Primitive | Purpose |
|---|---|
| `Lock` | Mutual exclusion — only one thread in the critical section at a time |
| `RLock` | Reentrant lock — same thread can acquire it multiple times without deadlocking itself |
| `Semaphore` | Allows up to N threads into a section simultaneously |
| `Event` | One thread signals; others wait for the signal |
| `Condition` | Threads wait until notified, often used with a shared state check |
| `Barrier` | Blocks threads until a fixed number have all reached the barrier point |

```python
sem = threading.Semaphore(2)   # only 2 threads allowed at once
event = threading.Event()
event.wait()      # blocks until event.set() is called elsewhere
```

### 11.7 Deadlocks

**Definition:** A deadlock occurs when two or more threads are each waiting for a resource the other holds, so none can proceed.

```python
lock_a = threading.Lock()
lock_b = threading.Lock()

def thread1():
    with lock_a:
        time.sleep(0.1)
        with lock_b:   # waits for lock_b, held by thread2
            pass

def thread2():
    with lock_b:
        time.sleep(0.1)
        with lock_a:   # waits for lock_a, held by thread1
            pass
# Classic deadlock: each thread holds what the other needs
```
**Prevention:** Always acquire multiple locks in a **consistent global order** across all threads.

### 11.8 `ThreadPoolExecutor`
```python
from concurrent.futures import ThreadPoolExecutor

def fetch(url):
    return f"Fetched: {url}"

urls = ["a.com", "b.com", "c.com"]
with ThreadPoolExecutor(max_workers=3) as executor:
    results = list(executor.map(fetch, urls))
print(results)
```

### 11.9 Interview Question
**Q: If Python has the GIL, why use threading at all?**

**Short Interview Answer:** "The GIL only prevents multiple threads from executing Python bytecode at the exact same instant — it doesn't prevent threads from being useful. For I/O-bound tasks like network requests or file reads, the GIL is released while a thread waits on I/O, so other threads can run during that wait. This means threading gives real speedups for I/O-bound workloads, even though it doesn't help — and can even hurt — CPU-bound workloads, where multiprocessing is the better tool."

### 11.10 Predict the Output
```python
counter = 0
def inc():
    global counter
    for _ in range(1000000):
        counter += 1

threads = [threading.Thread(target=inc) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print(counter == 4000000)
```
**Answer:** Usually `False` (non-deterministic — sometimes closer, sometimes far off, but rarely exactly correct without a lock).
**Interview Concept Tested:** `+=` is not atomic; concurrent unsynchronized access to shared state causes lost updates.

### Quick Revision
- GIL: only one thread runs Python bytecode at a time (CPython-specific).
- Threading helps I/O-bound tasks; not CPU-bound tasks.
- Race conditions arise from unsynchronized shared-state mutation.
- `Lock`/`RLock`/`Semaphore`/`Event`/`Condition`/`Barrier` — pick based on the coordination need.
- Deadlocks: prevent via consistent lock-acquisition ordering.
- `ThreadPoolExecutor` simplifies managing pools of worker threads.
