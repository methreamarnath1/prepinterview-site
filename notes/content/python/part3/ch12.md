# Chapter 12: Concurrency II — Multiprocessing

### 12.1 Why Multiprocessing?

**Definition:** Multiprocessing runs separate **processes**, each with its own Python interpreter and memory space — sidestepping the GIL entirely, enabling true parallel execution across CPU cores.

**When to Use:** CPU-bound workloads (heavy computation, image processing, number crunching) where threading can't help due to the GIL.

| Aspect | Threading | Multiprocessing |
|---|---|---|
| Memory | Shared | Separate (own memory space per process) |
| GIL impact | Limits to one thread executing bytecode at a time | Not affected — each process has its own GIL |
| Best for | I/O-bound | CPU-bound |
| Overhead | Low | Higher (process startup, memory duplication) |
| Communication | Shared variables (needs locks) | Explicit — Queue, Pipe, shared memory |

### 12.2 Basic `Process` Usage
```python
from multiprocessing import Process

def worker(name):
    print(f"Process {name} running")

if __name__ == "__main__":   # REQUIRED on Windows/spawn-based systems
    p1 = Process(target=worker, args=("A",))
    p2 = Process(target=worker, args=("B",))
    p1.start()
    p2.start()
    p1.join()
    p2.join()
```
**Why the `if __name__ == "__main__":` guard is essential:** On platforms using the "spawn" start method (default on Windows and macOS), child processes re-import the main module. Without the guard, this causes infinite recursive process creation.

### 12.3 `Pool` — Parallelizing a Function Over Data
```python
from multiprocessing import Pool

def square(x):
    return x * x

if __name__ == "__main__":
    with Pool(processes=4) as pool:
        results = pool.map(square, range(10))
    print(results)
```

### 12.4 Inter-Process Communication — `Queue` and `Pipe`

Since processes don't share memory, they need explicit channels to exchange data.

```python
from multiprocessing import Process, Queue

def producer(q):
    q.put("data from child process")

if __name__ == "__main__":
    q = Queue()
    p = Process(target=producer, args=(q,))
    p.start()
    p.join()
    print(q.get())   # "data from child process"
```

```python
from multiprocessing import Process, Pipe

def worker(conn):
    conn.send("hello from child")
    conn.close()

if __name__ == "__main__":
    parent_conn, child_conn = Pipe()
    p = Process(target=worker, args=(child_conn,))
    p.start()
    print(parent_conn.recv())   # "hello from child"
    p.join()
```

| Tool | Direction | Use Case |
|---|---|---|
| `Queue` | Many-to-many | General producer/consumer between multiple processes |
| `Pipe` | Point-to-point (2 endpoints) | Fast, simple communication between exactly two processes |

### 12.5 Shared Memory

```python
from multiprocessing import Process, Value, Array

def increment(shared_val):
    with shared_val.get_lock():
        shared_val.value += 1

if __name__ == "__main__":
    counter = Value("i", 0)   # 'i' = C int type
    processes = [Process(target=increment, args=(counter,)) for _ in range(10)]
    for p in processes: p.start()
    for p in processes: p.join()
    print(counter.value)   # 10
```
**Why `get_lock()` matters:** Even with shared memory, concurrent writes need synchronization — the same race-condition risk from threading applies here.

### 12.6 Process Synchronization
`multiprocessing` provides its own versions of `Lock`, `Semaphore`, `Event`, similar to `threading`, but designed to work safely across process boundaries (since regular threading locks can't be shared between separate memory spaces).

### 12.7 Common Mistakes
- Forgetting the `if __name__ == "__main__":` guard — causes recursive process spawning or import errors on Windows/macOS.
- Assuming child processes see live updates to variables in the parent — they don't; each process gets its own **copy** of the parent's state at fork/spawn time (unless using explicit shared memory).
- Choosing multiprocessing for I/O-bound tasks — the overhead of process creation and IPC often makes it slower than plain threading or asyncio for I/O-heavy work.

### 12.8 Predict the Output
```python
from multiprocessing import Process

counter = 0

def increment():
    global counter
    counter += 1
    print(f"Inside process: {counter}")

if __name__ == "__main__":
    p = Process(target=increment)
    p.start()
    p.join()
    print(f"In main process: {counter}")
```
**Answer:**
```
Inside process: 1
In main process: 0
```
**Explanation:** The child process gets its own **copy** of `counter` — incrementing it there has no effect on the parent process's separate memory space.
**Interview Concept Tested:** Processes do NOT share memory by default, unlike threads.

### 12.9 Interview Question
**Q: When would you choose multiprocessing over threading in Python?**

**Short Interview Answer:** "I'd choose multiprocessing for CPU-bound work, like heavy numerical computation, because it sidesteps the GIL entirely by running separate processes with their own interpreters, allowing true parallelism across CPU cores. Threading is better suited for I/O-bound work, since the overhead of spawning processes and communicating between them via Queue or Pipe is much higher than the overhead of threads, which share memory directly."

### Quick Revision
- Multiprocessing = separate memory, separate GIL per process — real parallelism for CPU-bound work.
- Always guard entry point with `if __name__ == "__main__":`.
- `Queue`/`Pipe` for IPC; `Value`/`Array` for shared memory (still needs locks).
- Trap: child processes don't see live changes to parent-process globals.
