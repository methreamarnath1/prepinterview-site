# Chapter 5: Testing — unittest, pytest, Fixtures, Mocking

### 5.1 Why Automated Testing?

**Definition:** Automated tests are code that verifies other code behaves correctly, run repeatedly (e.g., on every change) to catch regressions early.

### 5.2 `unittest`
```python
import unittest

def add(a, b):
    return a + b

class TestAdd(unittest.TestCase):
    def test_positive_numbers(self):
        self.assertEqual(add(2, 3), 5)

    def test_negative_numbers(self):
        self.assertEqual(add(-1, -1), -2)

    def setUp(self):
        print("Runs before each test")

    def tearDown(self):
        print("Runs after each test")

if __name__ == "__main__":
    unittest.main()
```
**Key methods:** `assertEqual`, `assertTrue`, `assertFalse`, `assertRaises`, `assertIn`, `assertIsNone`.

```python
def divide(a, b):
    if b == 0:
        raise ValueError("cannot divide by zero")
    return a / b

class TestDivide(unittest.TestCase):
    def test_zero_division_raises(self):
        with self.assertRaises(ValueError):
            divide(10, 0)
```

### 5.3 `pytest` — Simpler, More Popular

```python
def add(a, b):
    return a + b

def test_add():
    assert add(2, 3) == 5

def test_add_negative():
    assert add(-1, -1) == -2
```
**Why It's Preferred Over `unittest`:** Plain `assert` statements (no `self.assertEqual` boilerplate), automatic test discovery, better failure output, and a powerful fixture system.

### 5.4 Fixtures
```python
import pytest

@pytest.fixture
def sample_data():
    return {"name": "Amar", "age": 21}

def test_name(sample_data):
    assert sample_data["name"] == "Amar"
```
**Why It's Used:** Fixtures provide reusable setup/teardown logic, injected automatically into any test function that names them as a parameter — avoiding repeated setup code.

### 5.5 Parameterization
```python
import pytest

@pytest.mark.parametrize("a,b,expected", [
    (2, 3, 5),
    (-1, 1, 0),
    (0, 0, 0),
])
def test_add(a, b, expected):
    assert add(a, b) == expected
```
**Why It's Used:** Runs the same test logic against multiple input/output pairs without duplicating test functions.

### 5.6 Mocking — `unittest.mock`

**Definition:** Mocking replaces a real object/function (often something slow, external, or non-deterministic — like an API call or database) with a fake stand-in during a test, so the test focuses only on the code under test.

```python
from unittest.mock import Mock, patch

def get_user_from_api(api_client, user_id):
    return api_client.fetch(user_id)

def test_get_user_with_mock():
    mock_client = Mock()
    mock_client.fetch.return_value = {"id": 1, "name": "Amar"}
    result = get_user_from_api(mock_client, 1)
    assert result["name"] == "Amar"
    mock_client.fetch.assert_called_once_with(1)
```

**`patch` — Replacing a real dependency temporarily:**
```python
import requests

def get_status(url):
    return requests.get(url).status_code

@patch("requests.get")
def test_get_status(mock_get):
    mock_get.return_value.status_code = 200
    assert get_status("http://example.com") == 200
```
**How `patch` works:** It temporarily replaces the named object (here, `requests.get`) with a `Mock`, for the duration of the test, then restores the original afterward — even if the test fails or raises.

**Interview Q: Why do we mock external dependencies in unit tests?**
**Answer:** "Unit tests should be fast, deterministic, and isolated — testing only the logic of the function under test. If a function calls a real API or database, the test becomes slow, dependent on network availability, and could produce different results each run. Mocking replaces that dependency with a controlled fake, so we can test our own logic's behavior in isolation, including edge cases like errors that would be hard to trigger against a real service."

### 5.7 Test Coverage
```bash
pip install coverage
coverage run -m pytest
coverage report
coverage html   # generates a browsable report
```
**Common Mistake:** Treating 100% coverage as proof of correctness — coverage only shows which lines *executed* during tests, not whether the test actually verified correct behavior meaningfully.

### 5.8 Common Interview Trap
**Wrong thinking:** "High test coverage means the code has no bugs."
**Correct thinking:** Coverage measures which lines ran, not whether assertions properly verified the expected behavior — you can have 100% coverage with weak/meaningless assertions.

### Predict the Output
```python
from unittest.mock import Mock

mock_obj = Mock()
mock_obj.some_method(1, 2, 3)
print(mock_obj.some_method.call_count)
mock_obj.some_method.assert_called_with(1, 2, 3)
print("assertion passed")
```
**Answer:**
```
1
assertion passed
```
**Explanation:** `Mock` objects auto-track every call made to them; `call_count` reflects the number of calls, and `assert_called_with` verifies the exact arguments of the most recent call.

### Quick Revision
- `unittest`: class-based, `self.assertX` methods, built into the standard library.
- `pytest`: plain `assert`, fixtures, parameterization — the modern standard.
- Fixtures: reusable setup, injected by naming as a parameter.
- Mocking: replace slow/external/non-deterministic dependencies with controlled fakes.
- `patch`: temporarily swaps a real object for a mock, restores it afterward automatically.
- Trap: coverage % measures lines executed, not correctness of assertions.
