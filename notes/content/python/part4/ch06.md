# Chapter 6: Debugging Practice & Practical Projects

### 6.1 Debugging Workflow
1. Reproduce the bug reliably.
2. Read the full traceback bottom-up — the last line names the exception, the frames above show the call chain that led there.
3. Use `print()` or `logging.debug()` for quick checks, or `breakpoint()` for interactive inspection.
4. Isolate — comment out / bisect code to narrow down the failing section.
5. Fix, then add a regression test so the bug can't silently return.

```python
def process(data):
    breakpoint()   # drops into pdb here — inspect variables interactively
    return data["value"] * 2
```
Inside `pdb`: `n` (next line), `s` (step into), `c` (continue), `p variable_name` (print), `l` (list source), `q` (quit).

### 6.2 Reading Tracebacks (Interview-Relevant)
```
Traceback (most recent call last):
  File "app.py", line 10, in <module>
    result = calculate(5, 0)
  File "app.py", line 5, in calculate
    return a / b
ZeroDivisionError: division by zero
```
**Interview Q: How do you read a Python traceback?**
**Answer:** "Read it bottom-up. The last line gives the exception type and message — the actual error. The frames above show the call stack that led there, ordered from where the error actually occurred (closest to the bottom) up to where execution started (top). This lets you trace exactly which function call chain caused the failure."

## Practical Projects

### Beginner Projects
1. **Calculator** — CLI tool using `argparse`, handling `+ - * /`, with `try/except` for division by zero and invalid input.
2. **Number Guessing Game** — uses `random.randint`, a loop with attempt counting, and input validation.
3. **To-Do CLI** — uses `json` for persistent storage, `argparse` subcommands (`add`, `list`, `done`, `remove`).
4. **Contact Manager** — dictionary-of-dictionaries data structure, CRUD operations, saved to JSON.
5. **Student Management System** — classes for `Student`, grade calculations, sorting by grade using `sorted(key=...)`.

### Intermediate Projects
1. **Expense Tracker** — `csv` module for storage, `datetime` for timestamps, `collections.defaultdict` for category totals.
2. **File Organizer** — `pathlib` + `shutil` to sort files into folders by extension.
3. **Log Analyzer** — `re` module to parse log lines, `Counter` to summarize error frequency.
4. **CSV/JSON Processor** — reads CSV, transforms with list comprehensions, writes JSON (and vice versa), demonstrating `csv.DictReader`/`json.dump`.
5. **API Client** — uses `requests`, handles pagination, retries with `time.sleep` backoff, custom exception classes for API errors.
6. **Automation Utility** — e.g., a script combining `os`/`shutil`/`schedule`-style timing to automate a repetitive file task.

### Advanced Projects
1. **Multithreaded Application** — a concurrent URL-status checker using `ThreadPoolExecutor` (builds on Part 3 Ch.11).
2. **Multiprocessing Application** — a CPU-bound image/number-crunching task parallelized with `Pool` (builds on Part 3 Ch.12).
3. **Asyncio Application** — a concurrent API-polling tool using `asyncio.gather` (builds on Part 3 Ch.13).
4. **Custom Iterator Project** — a paginated data-fetcher implementing `__iter__`/`__next__` (builds on Part 2's iterator protocol).
5. **Decorator-Based Utility** — a `@retry(times=3)` decorator factory with exponential backoff (builds on Part 3 Ch.3).
6. **Context-Manager Project** — a database-connection-style manager with `__enter__`/`__exit__` guaranteeing cleanup (builds on Part 3 Ch.4).
7. **Plugin/Module System** — dynamic plugin loading using `importlib`, demonstrating real-world use of introspection (builds on Part 3 Ch.6).

Each project intentionally reuses concepts from Parts 1–3, so building them is itself revision.

### Quick Revision
- Debug systematically: reproduce → read traceback bottom-up → isolate → fix → add regression test.
- Projects are chosen to reinforce specific chapters — treat them as applied revision, not separate learning.
